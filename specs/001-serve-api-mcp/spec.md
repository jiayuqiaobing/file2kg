# Feature Specification: serve 常驻服务（HTTP API + MCP，模型常驻消除冷启动）

**Feature Branch**: `001-serve-api-mcp`

**Created**: 2026-10-04

**Status**: Draft

**Input**: User description: "serve 常驻服务：HTTP API + MCP，模型常驻内存消除冷启动"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 常驻检索：一次启动，反复秒回 (Priority: P1)

用户有一份已建好的知识库，需要**反复**检索（自己边写边查，或把它当作某个应用的检索后端）。
今天每次检索都要重走一遍冷启动——导入依赖、加载嵌入模型，每次十几秒，批量使用无法忍受。

启动常驻服务后，模型只在首次需要时加载一次，之后常驻内存；后续每次检索都在亚秒级返回。
服务可选在启动时就把模型预热好，让**第一次**请求也不必等。

**Why this priority**: 这是本功能的核心价值，也是用户点名要解决的那件事——"模型常驻内存消除
冷启动"。没有它，HTTP 与 MCP 只是把一条慢命令包了一层壳；有了它，file2kg 才真正能作为检索
后端被反复调用。

**Independent Test**: 启动服务 → 连续发起多次检索 → 确认第 2 次起稳定亚秒级返回，且服务进程
内模型只加载过一次。单独交付这一条故事即可作为可用 MVP。

**Acceptance Scenarios**:

1. **Given** 一个已建好的库、服务尚未启动，**When** 用户执行启动命令，**Then** 服务就绪并报告
   它正在服务哪个库、绑定哪个嵌入模型、当前权限模式（只读/可写）与预热状态
2. **Given** 服务已就绪且模型已加载，**When** 客户端连续发起两次及以上检索，**Then** 每次都在
   亚秒级返回，且返回内容与命令行检索的结果语义一致（同样带来源、位置与相关度分数）
3. **Given** 服务已就绪，**When** 收到畸形或越界请求（空查询、条数超上限），**Then** 服务返回
   明确的拒绝说明并**保持存活**，不崩溃、不重新加载模型
4. **Given** 服务已就绪，**When** 用户停止服务，**Then** 服务干净退出，端口与文件句柄均被释放，
   可立即重新启动，不留半截状态

---

### User Story 2 - Agent 通过 MCP 接入，默认只读 (Priority: P2)

用户装了 Claude Code / Cursor 这类支持 MCP 的 Agent 工具。把 file2kg 配成一个 MCP 工具后，
Agent 能在用户提问时**主动**去本地知识库检索并引用来源，而不是让用户手动复制粘贴。

默认配置下，Agent 只能读——工具清单里根本没有写操作，因此不存在"Agent 误改库"的可能性。

**Why this priority**: 这是"任何 Agent 都能用"的兑现点，也是本项目对社区最稀缺的那一格
（同类工具里有 MCP 的少，MCP 默认只读的更少）。排在 P1 之后是因为：如果检索本身不常驻、不快，
Agent 的每次工具调用都要等冷启动，体验同样崩塌。

**Independent Test**: 在任一个 MCP 客户端里配置并连接本服务 → 客户端能列出可用工具 → 发起一次
检索并拿到带来源的结果 → 确认默认下**没有任何写工具**被暴露。

**Acceptance Scenarios**:

1. **Given** 服务以默认配置运行，**When** MCP 客户端连接，**Then** 可见工具清单**只包含读操作**
   （检索、库信息），且不含任何写操作
2. **Given** Agent 通过 MCP 发起检索，**When** 检索命中，**Then** 每条结果都带来源文件与位置
   （页码/标题），Agent 可据此引用到具体出处
3. **Given** Agent 通过 MCP 发起检索，**When** 库为空或关键词索引缺失，**Then** 返回 Agent 可
   理解的说明（例如"库为空，请先摄取"），而不是裸异常或空结果
4. **Given** 服务以默认配置运行，**When** Agent 尝试请求写操作，**Then** 该能力**根本不存在于
   工具清单中**（是"没有这个工具"，不是"有这个工具但报错"）
5. **Given** Agent 通过 MCP 接入，**When** 它在服务已预热后发起检索，**Then** 同样享受常驻加速
   （不因走 MCP 而重新冷启动）

---

### User Story 3 - 显式开启写权限，经服务触发增量摄取 (Priority: P3)

用户的文档目录在持续变化（笔记、手册、课程资料）。他希望 Agent 在发现新内容时能**主动**触发一次
增量摄取，而不用切回终端手动跑命令。

用户以显式方式开启写权限后，服务才暴露摄取能力；每一次摄取仍然产出正常的作业审计，与命令行
入口产出的审计同格式、同纪律。

**Why this priority**: 有价值但不是必需——P1/P2 已经交付了"常驻检索"这个主要价值。写权限意味着
服务从"只读查询后端"变成"可变更后端"，风险与责任都更高，所以它排最后，且**可以被独立剥离而不
影响前两个故事**。

**Independent Test**: 默认启动 → 确认摄取能力不可达 → 以显式开启写权限的方式重启 → 触发一次增量
摄取 → 确认库已按增量规则更新，且新产生了一份可查阅的作业审计。

**Acceptance Scenarios**:

1. **Given** 服务以**默认配置**运行，**When** 任何客户端尝试触发摄取，**Then** 请求被拒绝，
   且拒绝理由明确指向"写权限未开启"以及如何开启
2. **Given** 用户显式开启写权限并重启服务，**When** 客户端触发一次增量摄取，**Then** 库按增量
   规则更新（只处理变化与新增），并产出一份可查阅的作业审计
3. **Given** 写权限已开启，**When** 两个写请求同时到达，**Then** 服务串行处理（同一时刻至多一个
   作业），不产生交叉写坏的审计或库
4. **Given** 写权限已开启，**When** 一次摄取中部分文件失败，**Then** 失败文件在响应与审计中都
   如实可见，服务**不假装成功**
5. **Given** 写权限已开启，**When** 触发摄取，**Then** 服务不得让库出现"已变更但无对应审计"的
   状态

### User Story 4 - 服务自述：随时说清自己在服务什么 (Priority: P4)

用户或 Agent 需要随时确认："这个服务连的是哪个库、用的哪个嵌入模型、现在是不是只读"。

这一点在"一库一模"下尤其关键：客户端必须能知道自己连的库绑定的是哪个嵌入模型与维度，
否则可能拿着错误的假设去查询。

**Why this priority**: 运维与排障必需，但可以后补。它小、独立，且不影响主链路。

**Independent Test**: 向运行中的服务查询自身信息 → 返回库标识、绑定模型与维度、权限模式、
预热状态。

**Acceptance Scenarios**:

1. **Given** 服务在运行，**When** 客户端查询服务信息，**Then** 返回所服务的库标识、表名、
   绑定的嵌入模型与向量维度、权限模式、预热状态
2. **Given** 客户端请求的库所绑定的模型与服务当前使用的模型不一致，**When** 服务启动或首次
   访问该库，**Then** 服务**拒绝**提供该库的服务，并同时说明两边的模型名与维度
3. **Given** 服务在运行，**When** 客户端查询服务信息，**Then** 该查询本身不触发模型加载
   （不查询不应该把模型拉起来）

---

### Edge Cases

- **库不存在**：服务明确报错并给出"先运行摄取"的指引，而不是静默建一个空库
- **库为空 / 关键词索引缺失**：检索给出可读说明与补救指引，不返回裸异常
- **模型与库不匹配**：拒绝服务该库，说清两边模型名与维度（一库一模），绝不哑开
- **服务运行中，同一个库被命令行入口并发写入**：服务不得崩溃；读到的要么是上一个提交点、
  要么是新提交点，**不得读到半批数据**
- **端口被占用**：启动明确失败并说明原因，**不静默换端口**（诚实优先于"看起来能跑"）
- **请求参数越界**：条数超上限 / 负数 / 非整数 / 空查询 → 明确拒绝该请求，服务保持存活
- **库目录在服务运行期间被删除或移动**：明确报错，不得静默返回空结果
- **预热被显式请求但模型下载失败（无网络）**：如实报告失败原因与镜像设置指引；服务仍可继续以
  懒加载方式运行，不得因此启动失败或假装已预热
- **绑定到非本机地址**：需用户显式指定，且必须提示"此操作会把知识库暴露到网络"；若同时开启了
  写权限，暴露风险显著上升，须有额外的访问控制要求
- **服务被强制终止（kill）**：重启后不产生损坏的库或审计；未完成的作业按既有"未提交即未发生"
  的纪律处理

## Requirements *(mandatory)*

### Functional Requirements

**启动与边界**

- **FR-001**: 服务 MUST 以单条命令启动，默认服务本机当前目录下的默认库（库目录、表名沿用与
  命令行入口相同的默认值），无需任何配置文件即可跑起来
- **FR-002**: 服务默认 MUST 只绑定本机回环地址；绑定到非回环地址 MUST 由用户显式指定，且
  用户 MUST 在启动输出中看到"知识库已暴露到网络"的明确提示
- **FR-003**: 服务在默认（本地）模式下 MUST 不需要任何 API key 即可工作

**检索（读）**

- **FR-004**: 服务 MUST 提供检索能力，支持混合检索（默认）与纯向量检索两种模式，结果 MUST 与
  命令行入口的检索语义一致（同样带来源、位置与相关度分数）
- **FR-005**: 服务 MUST 在首次真正需要嵌入模型时才加载，并在进程存活期间常驻复用；
  MUST NOT 重复加载
- **FR-006**: 服务 MUST 提供显式预热能力（启动时即加载模型），但预热 MUST NOT 是默认行为
- **FR-007**: 所有只读能力（含服务自述、库信息）MUST NOT 触发模型加载

**写操作与权限**

- **FR-008**: 服务在未开启写权限时 MUST 只暴露读操作；写能力 MUST NOT 出现在能力清单中
  （是"不存在"，不是"存在但拒绝"）
- **FR-009**: 写权限 MUST 由用户以显式方式开启；当前权限模式 MUST 可在服务自述中观察到
- **FR-010**: 经服务触发的每一次摄取 MUST 产生一份独立的作业审计，格式与纪律 MUST 与其他入口
  产出的审计完全一致（可追溯、只追加、不静默）
- **FR-011**: 服务 MUST 串行处理写操作（同一时刻至多一个作业）；并发写请求 MUST 被排队或明确
  拒绝，MUST NOT 并行执行
- **FR-012**: 服务 MUST NOT 引入任何新的写入路径；所有写入 MUST 复用既有的单点写入与审计组件
  （对应宪法原则 III 的"写操作只经单点入口"）
- **FR-013**: 破坏性操作（删除、全量重建）MUST NOT 通过服务暴露（保留在命令行入口）

**库绑定与一致性**

- **FR-014**: 服务 MUST 在启动或首次访问库时校验模型/维度指纹；不匹配 MUST 拒绝服务该库，
  并同时说明两边的模型名与维度
- **FR-015**: 服务 MUST 提供自身信息查询：所服务的库、表名、绑定的嵌入模型与维度、权限模式、
  预热状态

**接口品质**

- **FR-016**: 服务的响应 MUST 是机器可读的结构化结果；错误 MUST 附带可操作的修复指引，
  MUST NOT 把裸异常抛给调用方
- **FR-017**: MCP 入口 MUST 以工具形式暴露能力，每个工具的描述 MUST 足以让 Agent 正确理解其
  用途与参数含义
- **FR-018**: 服务 MUST 在收到畸形或越界请求时保持存活，只拒绝该请求本身
- **FR-019**: 服务停止时 MUST 干净退出，释放端口与文件句柄，可立即重启
- **FR-020**: 服务的日志与错误信息 MUST NOT 泄漏密钥

### Key Entities *(include if feature involves data)*

- **服务实例（Serve Instance）**：一个常驻进程，绑定**一个**库（库目录 + 表名）、**一个**嵌入
  模型、**一种**权限模式（只读/可写）、**一个**预热状态
- **服务自述（Service Descriptor）**：库标识、表名、绑定的嵌入模型与向量维度、权限模式、
  预热状态——供客户端与 Agent 判断自己连的是什么
- **检索请求 / 结果**：查询文本、检索模式（混合/纯向量）、返回条数上限；结果为带来源、位置
  （页码/标题）与相关度分数的条目集合
- **摄取请求（写）**：目标目录与分块参数；产出物与命令行入口一致——一个作业号 + 一份作业审计
- **能力清单（Capability Manifest）**：当前服务对外暴露的能力集合；默认只含读操作，开启写权限后
  才追加写操作

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 服务就绪后的第 2 次及以后检索，响应时间中位数达到**亚秒级**，相比每次都冷启动的
  现有方式**快一个数量级**
- **SC-002**: 连续发起 100 次检索，进程内嵌入模型加载次数**恒为 1 次**
- **SC-003**: 默认配置下，客户端可见的写操作数量为 **0**
- **SC-004**: 未开启写权限时，写请求被拒绝的比例为 **100%**，且拒绝理由**全部**指向开启方式
- **SC-005**: 经服务触发的摄取作业 **100%** 产出可查阅审计；不存在"库已变更但无对应审计"的情况
- **SC-006**: 同一库、同一参数下，服务检索结果与命令行检索结果的一致率为 **100%**
- **SC-007**: 畸形与越界请求下，因请求本身导致的服务退出次数为 **0**（只拒绝请求，不退出）
- **SC-008**: 异常场景（空库、索引缺失、库不存在、模型不匹配）**100%** 返回可读指引，
  裸异常暴露次数为 **0**
- **SC-009**: 服务停止后，端口与文件句柄 **100%** 释放，可立即重启成功
- **SC-010**: 用户把已有知识库接入 Agent 的配置动作可**一次完成**，之后无需重复配置

## Assumptions

- **单库服务**：一次只服务一个库（一个库目录 + 一个表），与命令行入口的默认模型一致；
  多库路由不在本功能范围内
- **本机单用户**：定位是本机单用户工具，不是多租户服务；默认无认证。面向局域网/公网的暴露
  不在本功能范围内，若未来需要须单独立项（含认证与访问控制）
- **写范围保守**：写权限开启后暴露的是**增量摄取**；删除、全量重建等破坏性操作保留在命令行
  入口，不通过服务暴露
- **MCP 与 HTTP 共用同一个常驻服务**：Agent 通过 MCP 接入时同样享受模型常驻，不因走 MCP 而
  冷启动；不为 MCP 单起一个独立进程
- **不做文件监听**：服务不自动感知目录变化（文件监听不在本功能范围内）；摄取由显式请求触发
- **复用同一条检索路径**：服务与命令行使用同一套检索与打分语义，不引入第二套结果口径
- **库需先存在**：本功能不负责首次建库；库不存在时服务给出明确指引而非静默创建
- **端口冲突诚实失败**：默认端口沿用项目既有约定；端口被占用时明确失败，不静默改用其他端口
- **审计纪律沿用既有约定**：只追加、单写者、崩溃后"未提交即未发生"——服务不另立一套审计规则
