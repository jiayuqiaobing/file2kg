# Data Model: serve 常驻服务

**Feature**: `001-serve-api-mcp` | **Date**: 2026-10-04 | **Spec**: [spec.md](./spec.md)

本功能**不引入新的持久化格式**：库仍是 LanceDB 目录，审计仍是每作业一份 JSONL。
新增的都是在**服务进程内存中**构造的只读视图（服务自述、能力清单、请求/响应投影）。

---

## 一、复用的既有实体（不新增、不改动）

这些是 v0.1 已存在的数据契约（`src/file2kg/types.py`），服务必须**原样复用**，不得另立一套。

| 实体 | 来源 | 服务中的用途 |
|------|------|--------------|
| `Chunk` | `types.py` | 检索查询文本先包成 `Chunk` 再嵌入——与 CLI 走同一条路径 |
| `JobReport` / `AuditChunk` | `types.py` | 服务触发的摄取产出物，格式与 CLI 完全一致 |
| 库行（LanceDB row） | `store.py` | 检索的原始结果行 |
| 审计事件行 | `auditor.py` | 服务触发的摄取产出物 |

> **关键约束（读代码得出）**：`Store.query()` 返回的是 `.to_list()` 的**整行**，包含
> `vector` 列（完整嵌入向量）以及 `text_hash` / `emb_model`。CLI 只是挑了三列渲染表格。
> 服务**不得**把整行透传给客户端——必须投影成下表定义的 `SearchHit`。
> 否则每个检索响应都会带上 1024 维浮点数组，既浪费带宽也泄漏内部表示。

## 二、服务进程内构造的新实体

这些**只在内存中存在**，不落盘、不进 `types.py` 之外的持久化契约。

### 2.1 ServiceDescriptor（服务自述）

服务启动时构造一次，此后**不可变**。对应 FR-015、US4。

| 字段 | 类型 | 说明 | 来源 |
|------|------|------|------|
| `service` | string | 服务标识与版本，如 `file2kg/0.2.0` | 常量 |
| `db_dir` | string | 所服务的库目录 | 启动参数 |
| `table` | string | 表名 | 启动参数 |
| `model` | string | **库绑定的**嵌入模型名 | 建库元数据（一库一模） |
| `dim` | integer | 向量维度 | 建库元数据 |
| `mode` | enum | `read-only` \| `read-write` | 启动参数（默认 `read-only`） |
| `warm` | boolean | 模型是否已加载常驻 | `Embedder` 运行时状态 |
| `capabilities` | string[] | 当前对外暴露的能力名清单 | 能力清单（见 2.2） |

**校验规则**：
- `model` / `dim` MUST 取自**库元数据**（建库时写入的绑定），而不是当前进程的配置——
  这样客户端看到的是"这个库绑的是什么模型"，而非"服务想用什么模型"。
- 若二者不一致，服务 MUST 拒绝启动/拒绝服务（见状态机 3.2）。

### 2.2 CapabilityManifest（能力清单）

对应 FR-008、FR-009 与宪法原则 III 的"默认不存在"。**启动时一次性构造，运行期不可变。**

| 能力名 | 类别 | 出现条件 |
|--------|------|----------|
| `service_info` | read | **恒有** |
| `search` | read | **恒有** |
| `ingest` | write | **仅当** `mode == read-write` |

**不变量（本功能最重要的设计约束）**：
- 只读模式下，`ingest` MUST NOT 出现在清单里——**不是标记为禁用，而是不存在**。
- 这个不变量 MUST 在两个入口同时成立：
  - HTTP：写路由 MUST NOT 被注册（请求得到 **404**，而非 403）
  - MCP：写工具 MUST NOT 被注册（客户端工具列表里看不到）
- 权限模式**运行期不可切换**，只能重启服务变更。这是"默认不存在"能被证明的前提：
  清单在进程生命周期内是常量，测试可对其做必然性断言。

### 2.3 SearchRequest / SearchHit（检索投影）

对应 FR-004、FR-016。请求与响应**都是刻意收窄的**，不复用库行。

**SearchRequest**

| 字段 | 类型 | 必填 | 默认 | 校验 |
|------|------|------|------|------|
| `query` | string | 是 | — | 去空白后非空；超长拒绝 |
| `k` | integer | 否 | 10 | 1..50（与 CLI 的 `--k` 上限一致） |
| `hybrid` | boolean | 否 | true | — |

**SearchHit**（`vector` / `text_hash` **必须剔除**）

| 字段 | 类型 | 说明 |
|------|------|------|
| `chunk_id` | string | 内容哈希前 16 位，稳定标识 |
| `text` | string | 正文（已含面包屑前缀） |
| `source` | string | 来源文件（相对 docs 目录） |
| `heading` | string \| null | 面包屑标题 |
| `page` | integer \| null | 来源页码（PDF） |
| `score` | number | 相关度分数（来自库行的 `_relevance_score`） |

> `emb_model` 不放进每条命中——它由 `ServiceDescriptor` 统一说明，逐条重复是冗余。
> 若未来需要按模型过滤，再单独开字段（YAGNI）。

### 2.4 IngestRequest / JobSummary（写，仅 read-write 模式）

对应 FR-010、US3。产出物与 CLI 完全一致——一个作业号 + 一份审计文件。

**IngestRequest**

| 字段 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| `docs_dir` | string | 否 | 服务启动时的默认目录 | 待摄取目录 |
| `force` | boolean | 否 | false | 全量重挂 |

**JobSummary**（响应体，是 `JobReport` 的**投影**，不是新持久化格式）

| 字段 | 类型 | 来源 |
|------|------|------|
| `job_id` | string | `JobReport.job_id` |
| `files_total` / `ingested` / `dupes` / `skipped` / `failed` | integer | `JobReport` 同名字段 |
| `chunk_count` | integer | `len(JobReport.chunks)` |
| `audit_path` | string | 该作业审计文件路径（可追溯） |
| `skipped_files` | object | `JobReport.skipped_files`（source → 原因） |
| `errors` | object | `JobReport.errors`（source → 错误信息） |

> `JobSummary` MUST 保留 `skipped_files` 与 `errors`——这两个字段是宪法原则 IV
> "已知的不完美必须可见"在服务层的落点。缺了它们，服务就会"看起来成功"。

## 三、状态与转换

### 3.1 模型生命周期（懒惰 → 常驻）

```
[未加载] --首次检索/显式预热--> [已加载常驻] --进程退出--> (释放)
   ^                                    |
   +-- 默认启动后停留在此 -----------------+  且：只读能力（service_info）永不触发此转换
```

- 默认启动后停留在 **[未加载]**（宪法原则 II：预热非默认副作用，FR-006）
- 触发条件**只有两个**：显式预热；或首次真正需要嵌入的检索请求
- 一旦进入 **[已加载常驻]**，进程存活期间**不再退出**该状态（FR-005 / SC-002）
- `service_info` 查询 MUST NOT 触发转换（FR-007）——因此它不能顺带计算维度等需要模型的信息

### 3.2 库绑定校验（一库一模）

```
服务启动 / 首次访问库
   ├─ 库不存在 ──────────> 拒绝 + 指引"先运行 file2kg ingest"
   ├─ 库存在，模型/维度一致 ─> 正常服务
   └─ 库存在，模型名不一致 -> 拒绝服务该库，报出两边的模型名 + 库侧维度
      （请求侧维度不报：取它要先加载模型，与"预热非默认"冲突，见 plan.md）
```

- 校验发生在**打开库时**，复用 `Store` 既有的维度自检——服务层不得另写一套校验
- 维度取自库元数据，不依赖"先把模型加载起来算一下"（那样会破坏"未加载"状态）

### 3.3 写请求并发（FR-011）

```
写请求到达
   ├─ mode == read-only  -> 能力不存在（404 / 工具未注册）
   └─ mode == read-write
        ├─ 无作业在跑 -> 开始作业
        └─ 有作业在跑 -> 排队 或 明确拒绝（二选一，见 research.md 决策）
```

- **同一时刻至多一个作业**——这是宪法原则 IV 的直接推论：审计是单写者设计，
  两个并发作业写同一审计文件/库会破坏"只追加 + 单写者"的前提。

## 四、明确不复用 / 不新增的东西

- **不新增持久化格式**：不引入服务自己的状态文件、不引入新的审计格式
- **不新增数据契约文件**：新的数据形状都是"投影"，若将来需要跨模块共享，
  才按宪法"数据契约"一节移入 `types.py`
- **不对库 schema 做任何改动**：服务是只读视图 + 复用既有写入路径
